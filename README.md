# task-tracker-service

Сервис управления задачами: REST API + PostgreSQL + Kafka. Java 21, Spring Boot 3.5, Spring Data JPA, Spring Kafka, Spring Security.

## Модель данных

- **Task**: id, title (наименование), description, status (`NEW`, `IN_PROGRESS`, `DONE`, `CANCELLED`), assignee (User), version (optimistic locking)
- **User**: id, name, email

Онбординг пользователей вне scope задания — при первом запуске Flyway засеивает 5 тестовых пользователей (см. `GET /api/users`), их можно назначать исполнителями.

## Запуск

```bash
cp .env.example .env   # заполнить реальными значениями; .env в .gitignore, в репозиторий не попадает
docker-compose up -d --build
```

Поднимает PostgreSQL, Kafka (KRaft, без ZooKeeper) и сам сервис. API доступен на `http://localhost:8080`, Swagger UI — `http://localhost:8080/swagger-ui.html` (открыт без авторизации, кнопка Authorize настроена под Basic Auth ниже).

> Порты Postgres (`5433`) и Kafka (`9092`) на хосте забинжены только на `127.0.0.1` — это бэкенд-хранилища, наружу торчать не должны. Порт Postgres сдвинут с дефолтного `5432`, чтобы не конфликтовать с локально установленным PostgreSQL.

## Авторизация

Все `/api/**` эндпоинты закрыты HTTP Basic Auth. Полноценный домен пользователей/ролей не строится — заданием онбординг явно вынесен за рамки, а модель `User(id, name, email)` не рассчитана на хранение credentials. Basic Auth — единственная сервисная учётка, чтобы API не было полностью анонимным.

Креды берутся из переменных окружения `API_USERNAME`/`API_PASSWORD`, дефолтов нет, обе обязаны быть непустыми — без них (или с пустым значением) приложение не запустится. В `.env.example` — плейсхолдеры для локального запуска, реальные значения — только в `.env` (не коммитится).

```bash
curl -u apiuser:<password-из-.env> localhost:8080/api/tasks
```

Swagger UI, `/v3/api-docs`, `/actuator/health`, `/actuator/info` доступны без авторизации.

**Важно, если это когда-либо выйдет за пределы localhost:** HTTP Basic передаёт креды в Base64 — это кодирование, не шифрование, эквивалент открытого текста при перехвате трафика. Сервис обязан стоять за TLS-терминацией (ingress/reverse-proxy/LB) в любом окружении, кроме локального docker-compose. Rate limiting на этот эндпоинт тоже не сделан (см. ниже) — без него единственная сервисная учётка уязвима для перебора пароля.

## REST API

| Метод | Путь                        | Описание                          |
|-------|-----------------------------|------------------------------------|
| GET   | `/api/tasks?page=&size=`    | Список задач с пагинацией (сортировка по id desc по умолчанию, максимум 100 записей за раз, ответ вида `{"content":[...],"page":{"size","number","totalElements","totalPages"}}`) |
| GET   | `/api/tasks/{id}`           | Задача по id                       |
| POST  | `/api/tasks`                | Создать задачу                     |
| PATCH | `/api/tasks/{id}/assignee`  | Назначить исполнителя              |
| PATCH | `/api/tasks/{id}/status`    | Сменить статус                     |
| GET   | `/api/users`                | Список пользователей (для выбора исполнителя) |

### Примеры

```bash
AUTH="-u apiuser:change-me-dev-password"

# Создать задачу
curl $AUTH -X POST localhost:8080/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"title": "Написать отчёт", "description": "Квартальный отчёт"}'

# Список задач
curl $AUTH "localhost:8080/api/tasks?page=0&size=10"

# Назначить исполнителя (id=1 — Alice Ivanova из сида)
curl $AUTH -X PATCH localhost:8080/api/tasks/1/assignee \
  -H "Content-Type: application/json" \
  -d '{"assigneeId": 1}'

# Сменить статус
curl $AUTH -X PATCH localhost:8080/api/tasks/1/status \
  -H "Content-Type: application/json" \
  -d '{"status": "IN_PROGRESS"}'
```

Параллельное изменение одной и той же задачи (например, два одновременных `PATCH /status`) — второй запрос получает `409 Conflict` (оптимистическая блокировка через `@Version`), а не тихо теряет данные.

## Kafka-события

- `task.created` — публикуется после создания задачи
- `task.assignee-changed` — публикуется после назначения исполнителя

Ключ сообщения — `taskId`. Событие публикуется через `@TransactionalEventListener(phase = AFTER_COMMIT)` — только после успешного коммита в БД, поэтому невозможна ситуация «событие ушло, а задача не сохранилась». Обратная сторона этого выбора — доставка at-most-once: если процесс упадёт между коммитом и отправкой в Kafka, событие потеряется. Для тестового задания это осознанный компромисс; production-путь для at-least-once — Transactional Outbox.

`TaskAssigneeChangedEvent` содержит только `assigneeId` (без имени/email) — событие не должно тащить PII, которое может протухнуть или утечь в логи при сбое отправки.

```json
// task.created
{"taskId": 1, "title": "...", "description": "...", "occurredAt": "..."}
// task.assignee-changed
{"taskId": 1, "assigneeId": 1, "occurredAt": "..."}
```

## NFT и устойчивость к нагрузке

- До 100 000 задач: пагинация с явной сортировкой по `id` (без неё Postgres не гарантирует порядок строк между запросами — на активно изменяемой таблице это давало дубли/пропуски страниц), максимум 100 записей за один ответ (`spring.data.web.pageable.max-page-size`).
- До 10 000 пользователей: `GET /api/users` пока не пагинирован — при таком объёме отдаёт весь список одним ответом. Известное ограничение, не исправлено в этой итерации.
- `idx_tasks_assignee_id`/`idx_tasks_status` заложены под будущую фильтрацию (`GET /api/tasks?status=&assigneeId=` сейчас не реализован) — сами по себе текущие запросы (`findAll`, `findById`) их не используют.

## Безопасность: что сделано и что осталось

Проект прошёл два раунда независимого архитектурного/security/code-review (человек+агенты) с живой проверкой на поднятом стенде — не только чтением кода. Ниже — то, что реально проверено, и то, что осталось осознанно.

**Сделано и проверено вживую:**
- HTTP Basic Auth на всех `/api/**` (401 без креденшлов, 401 на неверный пароль, таймингом на несуществующего юзера не отличить от неверного пароля — брутфорс username через тайминг не работает); Swagger UI умеет "Authorize" (OpenAPI `securityScheme`)
- Отдельная непривилегированная Postgres-роль (`app_runtime`, только SELECT/INSERT/UPDATE/DELETE через `ALTER DEFAULT PRIVILEGES`) для рантайма приложения. Проверено эскалацией: `CREATE TABLE`/`DROP TABLE`/чтение `pg_authid`/`SET ROLE`/суперюзерство — везде `permission denied`. Flyway для DDL-миграций подключается отдельной учёткой-владельцем схемы (`SPRING_FLYWAY_USER/PASSWORD`); служебная таблица `flyway_schema_history` отдельно защищена от DML рантайм-роли Flyway-колбэком (`afterMigrate.sql`)
- Никаких паролей с дефолтами в коде — `DB_PASSWORD`, `API_USERNAME`, `API_PASSWORD` обязательны и не могут быть пустыми (валидация `@NotBlank`), без них приложение не стартует
- Порты Postgres/Kafka на хосте только на `127.0.0.1` — проверено попыткой подключения с IP в локальной сети (`Connection refused`), порт приложения (8080) открыт намеренно — это и есть сам API
- Секреты не закоммичены — `docker-compose.yml` ссылается на `.env` (gitignored), в репозитории только `.env.example` с плейсхолдерами
- Контейнер приложения — non-root пользователь, `.dockerignore`, минимальный набор пакетов в рантайм-образе
- Лимиты на размер тела запроса и длину `description`, кап на размер страницы пагинации (запрошенный `size=100000` реально клампится до 100, ответ содержит стабильный `page`-объект, а не сырой `PageImpl`)
- PII не публикуется в Kafka-событии о назначении исполнителя (`assigneeId` без имени/email); учтите, что `task.created` по-прежнему несёт свободный `title`/`description` — туда PII в принципе может положить сам вызывающий, это не controllable на уровне события
- Неизвестные пути/методы отдают корректные 404/405/415, а не 500 со стектрейсом в логе
- Актуальные версии зависимостей на момент последнего бампа (Spring Boot 3.5.16, Spring Security 6.5.11, Tomcat 10.1.55, Logback 1.5.34, pgjdbc 42.7.11, Spring Framework 6.2.19, kafka-clients 3.9.2) — ни один открытый CVE в затронутых компонентах на используемый функционал (Basic Auth, JDBC, JSON) не применим

**Осознанно не сделано (задокументировано, не забыто):**
- **Spring Boot 3.x уже вне OSS-поддержки** (ветка 3.5 потеряла поддержку 2026-06-30, 3.5.16 — последний патч без дальнейших обновлений). Актуальная линия — Spring Boot 4.1.x, но миграция трогает Jackson 3, JUnit 6, новые дефолты Spring Security 7, требует отдельного регрессионного прогона — сознательно не делалась в рамках этой итерации. Это реальный компромисс между актуальностью и риском непроверенных изменений, а не то, что "будет решено само" — если появится CVE именно в используемых частях 3.5.x, патча от Spring не будет.
- **Полноценная auth-модель с ролями** — текущая Basic Auth защищает API от анонимного доступа единой учёткой, но не разграничивает права между разными вызывающими и не даёт аудита "кто именно вызвал". Для реального прод-сценария — OAuth2/JWT с ролями, привязанными к домену пользователей (потребует расширения модели `User`, которая сейчас описана заданием как `id, name, email`).
- **TLS терминация и rate limiting перед Basic Auth** — единственная точка входа аутентификации без анти-брутфорс защиты и без шифрования на уровне приложения (см. предупреждение в разделе "Авторизация" выше). В проде — TLS на ingress/LB и throttling там же или через Bucket4j.
- **TLS/SASL на Kafka** — PLAINTEXT-листенеры, приемлемо для локального docker-compose, не для прода.
- **Идемпотентность `POST /api/tasks`** — повторный запрос (например, ретрай клиента после таймаута) создаёт дубль задачи и второе Kafka-событие. `Idempotency-Key` не реализован.
- **Валидация переходов статуса** — `PATCH /status` принимает любой переход (`DONE → NEW` пройдёт). В задании правила переходов не описаны; если появятся — это `EnumSet` в `TaskStatus`, не более.
- **Наблюдаемость** — только `health`/`info` в actuator, нет метрик (Micrometer/Prometheus), нет structured logging/traceId. При потере события из-за недоступной Kafka в лог пишется только `ERROR` без корреляции с конкретным HTTP-запросом.
- **Миграции внутри процесса приложения, а не отдельным шагом** — Flyway запускается при старте самого сервиса под отдельной (но всё ещё привилегированной) учёткой; в проде миграции обычно выносят в отдельный шаг деплой-пайплайна, чтобы рантайм-процесс вообще не знал DDL-креды.
